# Syolana Partner Automation — рекомендуемая архитектура

## 1. Владение

Каждый партнёр:
- регистрирует домен на себя и в своём аккаунте;
- владеет аккаунтом хостинга;
- владеет GitHub-репозиторием сайта;
- является владельцем и публикатором своего контента.

Syolana:
- предоставляет шаблон сайта;
- поставляет темы, плеер, иммерсивные компоненты и обновления;
- предоставляет редактор/автоматизацию публикаций;
- может проводить техническую и контентную модерацию по правилам сервиса.

Раздельный домен и хостинг уменьшают смешение ролей, но не освобождают Syolana от ответственности за собственные действия, обработку данных, код, рекламу или конкретные решения по публикации.

## 2. Хостинг и домен

Рекомендуемый старт:
- бесплатный GitHub Pages или Cloudflare Pages в аккаунте партнёра;
- собственный домен партнёр покупает и оформляет на себя;
- если домена пока нет, временно используется бесплатный технический поддомен хостинга.

Не регистрировать домены партнёров на Syolana, если цель — сохранить независимое владение.

## 3. Шаблон

Один эталонный Syolana Partner Template:
- базовые страницы;
- лента;
- плеер;
- подключение Syolana Core;
- редактор публикаций;
- проверка лицензии;
- GitHub Actions для сборки/публикации.

Новый партнёр получает собственную копию шаблона в своём аккаунте.

## 4. Syolana Core

Премиальные функции подключаются централизованно:
- темы;
- режим созерцания;
- иммерсивные книги;
- плеер;
- обновления дизайна.

Entitlement API проверяет partner_id, домен и срок доступа. После окончания платного периода премиальный слой перестаёт выдаваться, а собственный сайт и контент партнёра остаются у него.

Нельзя гарантировать 100% защиту уже загруженного в браузер кода/ассетов. Техническая защита дополняется лицензией и условиями использования.

## 5. Публикации без ежедневной ручной работы

Идеальный поток:

Партнёр -> простая форма/редактор на своём сайте -> Syolana Publishing Gateway -> черновик/PR в репозитории партнёра -> автоматические проверки -> модерация -> merge -> GitHub/Cloudflare Pages публикует сайт.

Партнёру не нужно заходить в GitHub.

Дополнительные источники позже:
- RSS/Atom;
- официальный API соцсети;
- письмо на уникальный publishing-адрес;
- импорт из внешнего редактора.

HTML-скрейпинг соцсетей не использовать как основу: он хрупкий и может нарушать правила площадок.

## 6. Модерация

Автоматические проверки:
- структура поста;
- размеры и форматы медиа;
- битые ссылки;
- запрещённый HTML/JS;
- дубликаты;
- базовые правила Syolana.

Контентная проверка:
- автоматическая модель может готовить решение/правки;
- спорные случаи уходят в очередь;
- решение и основания сохраняются в журнале.

Для полностью автоматической публикации нужен отдельный API/бот. Текущая беседа ChatGPT не является постоянно работающим серверным процессом.

После появления очереди можно настроить периодическую задачу, которая проверяет новые PR и публикует прошедшие правила записи.

## 7. Доступ Syolana к сайту партнёра

Лучший вариант — GitHub App с минимальными разрешениями:
- Contents: read/write только для выбранного репозитория;
- Pull Requests: read/write;
- Metadata: read.

Партнёр сам устанавливает приложение на свой репозиторий и в любой момент может отозвать доступ.

Не просить у партнёров пароли от GitHub, Cloudflare или домена.

## 8. Договоры

Полностью без условий сотрудничества работать не стоит.

Для обычных партнёров можно использовать одну стандартную публичную оферту/лицензионные условия и электронное присоединение:
- кто владеет доменом и контентом;
- кто отвечает за права на публикации;
- что именно предоставляет Syolana;
- что отключается после окончания доступа;
- цена/период определяются в индивидуальном предложении до оплаты;
- порядок жалоб и удаления;
- правила модерации.

Для издательств, площадок и сложных интеграций — отдельный договор.

## 9. Следующий технический этап

1. Создать отдельный GitHub Template Repository.
2. Собрать один тестовый партнёрский сайт в отдельном аккаунте/репозитории.
3. Подключить GitHub App.
4. Сделать Publishing Gateway.
5. Сделать entitlement API.
6. Провести весь путь: создание -> пост -> модерация -> публикация -> окончание доступа.
7. Только после этого масштабировать на новых партнёров.
